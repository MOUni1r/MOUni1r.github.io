01

Data foundation

The workflow combines data-quality checks, domain-driven feature engineering, stratified train/validation/test splits, outlier handling learned from training data, model comparison, and threshold tuning using validation data only.

Data quality

14,999 records were available. 700 missing churn labels were removed, leaving 14,299 labeled users. Duplicate rows were 0.

Feature engineering

Behavioral features included km per driving day, session ratios, professional-driver flags, km per hour, km per drive, and drives per session.

Model comparison

Logistic Regression, Random Forest, and XGBoost were evaluated. XGBoost had the strongest validation recall among the ensemble models.

Decision threshold

The threshold was tuned on validation data rather than the test set, explicitly trading precision for higher churn recall.

04

What the model says

The headline result is useful only when paired with the trade-offs and statistical context around it.

Key finding

Threshold choice changed the business trade-off.

52.47% recall

At the default 0.50 threshold, test recall was 17.16%. A validation-only threshold of 0.223 was selected to target 50% recall. On the untouched test set, that threshold produced 52.47% recall, 35.95% precision, 42.66% F1, and 75.00% accuracy. The threshold improves capture of churners at the cost of more false positives.

05

What I'd recommend

A churn score only creates value once it is connected to a specific, testable retention action.

01

Use the model output as a prioritized outreach list for the retention team, not as a final judgment on any single user.

02

Set the decision threshold from the real cost of a wasted retention offer versus the value of a saved user. The 0.223 threshold shown here is an illustrative operating point, not a business-approved one.

03

Before rolling out a retention campaign built on this model, run it as a controlled test against a holdout group to confirm the intervention itself reduces churn, not just that the targeting is accurate.

04

Revisit the model with richer behavioral data, such as in-app friction events or support tickets, since the current feature set puts a ceiling on how much churn risk can be explained.

06

Limitations & next steps

A strong case study should make its boundaries visible.

01The dataset is simulated for educational use and is aggregated at monthly level.
02A production system would need richer drive-level behavior and fresh representative data.
03The selected threshold should be revisited when the actual business cost of false positives and false negatives is known.
